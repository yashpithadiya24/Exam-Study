1. Application Layer અને Network Application

Application Layer TCP/IP stackની top layer છે. User-facing software (browser, email client, chat app) network પર કેવી રીતે information exchange કરે તે rules/protocols define કરે છે. Actual signal transmission નીચેની layers કરે છે.

સરળ analogy: Restaurantમાં user customer છે, application layer waiter જેવી request સમજાવી kitchen સુધી પહોંચાડે છે અને જવાબ પાછો આપે છે.

આ layer શા માટે જરૂરી?

  • User-level services: web browsing, email, file transfer, remote login.
  • Standardization: message format અને communication rules સરખા હોવાથી અલગ vendorsનાં devices/software વાત કરી શકે.
  • Interoperability: browser અને web server common protocol વડે કામ કરે છે.

Network application architecture

Client–ServerServer સામાન્ય રીતે always-on અને જાણીતા IP/hostname પર રહે. Client serverને request કરે; clients સામાન્ય રીતે એકબીજાને સીધું service આપતા નથી. Example: browser + website server.
P2P (Peer-to-Peer)Peers સીધા એકબીજા સાથે communicate કરે અને service લે પણ આપે. નવા peers resources પણ લાવે. Self-scalability હોઈ શકે, પણ peersની availability/IP બદલાવથી management મુશ્કેલ.

Process અને Socket

Process એટલે executionમાં ચાલતો program. Client process communication શરૂ કરે; server process contactની રાહ જુએ. Same hostમાં IPCથી; અલગ hostsમાં messagesથી communication થાય.

Socket application process અને transport layer વચ્ચેનું software interface. Socket address સમજવા માટે: IP address + port number + transport protocol (TCP/UDP).

Applicationની transport જરૂરિયાતો

  • Reliability: Email/file transferમાં data ખોવાય નહીં અને order સાચો રહે તે જરૂરી.
  • Throughput: Video/mediaને ચોક્કસ minimum data rate જોઈએ હોઈ શકે; elastic app ઉપલબ્ધ rate મુજબ ચાલે.
  • Timing: Live call અને interactive gameમાં ઓછો delay જરૂરી.
  • Security: Encryptionથી dataને સુરક્ષિત કરવો.

2. TCP vs UDP

TCPUDP
Connection-oriented; પહેલાં connection setupConnectionless; setup handshake નહીં
Reliable, ordered byte streamDelivery/order guarantee નથી
Retransmission, flow/congestion controlTransport layerમાં reliability/flow/congestion control નથી
વધુ overhead; reliability જરૂરી હોય ત્યાંઓછું overhead, ઓછો latency overhead; real-time appsમાં ઉપયોગી
Web/HTTP (પરંપરાગત HTTP), FTP, SMTP, TelnetDNS queries, SNMP, real-time voice/videoમાં સામાન્ય
Trick: TCP = Trustworthy & ordered; UDP = Use Directly, no delivery promise. UDP એટલે હંમેશાં ઝડપી જ હોય એવું નહીં—તે setup/reliability overhead ઓછો કરે છે, પરંતુ network સ્થિતિ અને app પર performance આધારિત છે.

આ બંને endpointsની reachability અને initial sequence information synchronize કરવા connection સ્થાપિત કરે છે.

Written question: TCP અને UDPની definition, connection type, reliability, ordering, control અને examples tableમાં લખો. Live audio/video માટે latency મહત્વની હોય તો UDP યોગ્ય હોઈ શકે; પરંતુ application પોતે recovery/ordering ઉમેરે તો વર્તન બદલાય.

3. Web, HTTP અને HTTPS

World Wide Web (WWW) Internet પર ઉપલબ્ધ linked documents/resourcesની service છે. Resources URL વડે ઓળખાય અને hyperlinks વડે જોડાય. મુખ્ય ભાગો: browser, web server, web pages/objects.

એક webpageમાં base HTML file અને અન્ય objects (images, CSS, scripts વગેરે) હોઈ શકે. દરેક objectનો URL હોય છે. URLમાં સામાન્ય રીતે host/domain અને path ઓળખાય.

HTTP

HyperText Transfer Protocol Application layer protocol છે. Browser HTTP request મોકલે છે; server HTTP response આપે છે. HTTP stateless છે—મૂળ protocol પોતે અગાઉની requestનો user state યાદ રાખતો નથી; cookies/sessionથી state રાખી શકાય.

HTTP vs HTTPS

HTTPHTTPS
Plain HTTP; default port 80HTTP over TLS; default port 443
Application-level content encrypted હોવાની guarantee નથીTLS encryption, integrity અને server authentication આપે (certificate validation યોગ્ય હોવી જોઈએ)
Untrusted networks પર content વાંચાઈ/બદલાઈ શકેNetwork પર content confidentiality અને tampering સામે protection

SSL/TLS: TLS secure channel બનાવે છે; SSL જૂનું/deprecated નામ/technology છે. સામાન્ય રીતે “HTTPS = HTTP + TLS”.

Exam line: HTTP stateless protocol છે; Cookies જેવી mechanisms user/session state જાળવવામાં મદદ કરે છે.

4. HTTP Connections, Messages અને Status Codes

Non-persistent vs Persistent HTTP

Non-persistentPersistent
દરેક object માટે અલગ TCP connection ખોલે/બંધ કરેએક TCP connection પર અનેક request/response થઈ શકે
Repeated setup overhead વધારેConnection reuseથી overhead ઘટે
PDF મુજબ HTTP/1.0નું defaultHTTP/1.1માં persistent connection સામાન્ય default
Calculation — RTT idea
Non-persistent HTTPમાં એક object માટે અંદાજે 1 RTT TCP setup + 1 RTT request/first response સુધી + object transmission time લાગી શકે. એટલે N objects serial રીતે માંગવામાં આવે તો અંદાજે 2N RTT + total transmission time. આ simplified model છે; parallel connections, caching અને modern HTTP behaviorથી વાસ્તવિક સમય બદલાય છે.

HTTP requestનું structure

Request line → Headers → Blank line → (Optional) Body

ઉદાહરણ: GET /index.html HTTP/1.1 — method, path અને HTTP version. Headersમાં Host, Accept, Cookie વગેરે હોઈ શકે.

HTTP responseનું structure

Status line → Headers → Blank line → (Optional) Body

Status lineમાં HTTP version, status code અને reason phrase હોય છે.

મહત્વના status codes

Code groupઅર્થExample
1xxInformational100 Continue
2xxSuccess200 OK, 201 Created
3xxRedirection301 Moved Permanently, 304 Not Modified
4xxClient-side request error400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found
5xxServer-side error500 Internal Server Error, 503 Service Unavailable
Trick: 2 = Success, 3 = Redirect, 4 = Client mistake, 5 = Server trouble.

5. Cookies, Web Cache અને Proxy

Cookies

Browserમાં સંગ્રહાતી નાની data values; website userને ઓળખી શકે અને preferences/session/cart જેવી state રાખી શકે. PDF મુજબ cookie systemના ચાર ભાગ: HTTP requestમાં Cookie header, responseમાં Set-Cookie header, browserમાં cookie file/storage, અને website backend database.

Use cases: login/session, shopping cart, personalization/recommendations, authorization state. Cookieમાં sensitive information સીધી રાખવી યોગ્ય નથી; server-side session અને યોગ્ય security attributes જરૂરી છે.

Web Cache / Proxy Cache

Clientની HTTP request origin serverને બદલે પહેલા cache સુધી જાય. Object cacheમાં હોય અને valid હોય તો તરત આપે (cache hit); ન હોય તો origin server પાસેથી મેળવી clientને આપે (cache miss).

→ miss

ફાયદા: Response time ઘટે, repeated content માટે upstream traffic/Internet access-link load ઘટે.

Forward Proxy, Reverse Proxy, Load Balancer

Forward ProxyClient તરફથી request કરે; client identity/traffic control, filtering અથવા caching માટે.
Reverse ProxyServer/applicationની આગળ ઊભું રહે; બહારના clientsને backend serversથી અલગ રાખે, TLS termination/caching વગેરે કરી શકે.
Load BalancerIncoming requestsને ઘણા backend serversમાં વહેંચે જેથી capacity અને availability સુધરે.
યાદ રાખો: Forward proxy = clientની તરફ; Reverse proxy = serverની આગળ; Load balancer = requests વહેંચે.

6. FTP, Telnet અને SSH

FTP — File Transfer Protocol

Network પર files upload/download કરવા client-server protocol; TCP વાપરે છે. PDFમાં બે TCP connections દર્શાવ્યાં છે:

  • Control connection: TCP port 21; login, commands, directory change, put/get.
  • Data connection: File data transfer; પરંપરાગત FTP active modeમાં port 20નો ઉપયોગ કરે છે; actual behavior active/passive mode પ્રમાણે બદલાય.

FTP server userની authentication અને current directory જેવી state જાળવી શકે છે.

Telnet vs SSH

TelnetSSH
Remote login/command execution; TCP port 23Secure remote login/command execution; TCP port 22
Traffic સામાન્ય રીતે plaintext; સુરક્ષિત network બહાર જોખમીEncrypted channel; authentication અને integrity protection
Legacy/teaching environmentsModern secure administration માટે preferred

SSH working — સરળ steps

  1. Client server સાથે connection શરૂ કરે.
  2. Server host key/certificate-type identity information રજૂ કરે; client તેને verify કરે.
  3. Key exchangeથી session keys બને.
  4. Session encryption પછી login/commands સુરક્ષિત રીતે જાય.
Port trick: FTP control 21, Telnet 23, SSH 22. “SSH = secure shell = 22”.

POP3ના ત્રણ phases

IMAP: Messages server પર રાખે; folders, search અને partial message retrievalને support કરે—બધા devicesમાં same mailbox sync રાખવા યોગ્ય.

Post office trick: SMTP = મોકલો; POP3 = download/collect; IMAP = server mailbox sync.
Correction note: Slidesમાં SMTP માટે port 25 અને secure submission માટે quizમાં 587 છે. Productionમાં TLS/STARTTLS અને provider configuration પ્રમાણે port/setting તપાસવી.

8. SNMP — Network Management

Simple Network Management Protocol routers, switches, servers, firewalls, printers જેવા devicesને monitor/manage કરવા માટેનું Application Layer protocol. PDF મુજબ UDP અને ports 161/162 સામાન્ય છે.

Manager / NMSCentral monitoring system; requests મોકલે, responses/traps મેળવે.
AgentManaged device પર ચાલે; deviceની management information વાંચે/બદલે અને report કરે.
MIB / OIDMIB management variablesની structured collection; OID કોઈ specific object/value ઓળખે.

મહત્વના operations

Operationકામ
GETAgent પાસેથી value વાંચવી (જેમ CPU/memory statistic)
SETAgent પર configurable value બદલવી
TRAPAgent તરફથી managerને unsolicited event notification; acknowledgementની રાહ નથી
INFORMNotification જે માટે acknowledgement/response અપેક્ષિત હોય
Mnemonic: GET = વાંચો, SET = બદલો, TRAP = તરત જાણ, INFORM = જાણ + acknowledgement.

10. DNS — Domain Name System

DNS domain/host nameને IP addressમાં resolve કરતું distributed, hierarchical naming system છે. માણસ example.com યાદ રાખે છે; networkને IP address જોઈએ.

Hierarchy

Root DNS
↓
TLD DNS (.com, .org, .in)
↓
Authoritative DNS (domainના records)

Local DNS resolver query handle કરે છે અને cacheમાં મળેલા results રાખી શકે છે.

Resolutionના સામાન્ય steps

  1. Browser/OS local cache તપાસે.
  2. Local resolver પાસે query જાય.
  3. Cacheમાં ન હોય તો resolver root → TLD → authoritative DNS તરફ information મેળવે (iterative processનું સામાન્ય વર્ણન).
  4. Authoritative server record આપે; resolver response clientને આપે અને TTL પ્રમાણે cache કરી શકે.

Iterative vs Recursive Query

IterativeServer પોતાની પાસે જવાબ ન હોય તો આગળના DNS serverનું referral આપે; requester આગળ પૂછે.
RecursiveAsked DNS serverથી complete answer મેળવવાની જવાબદારી અપેક્ષિત; તે અન્ય serversને પૂછે છે અથવા cached/authoritative answer આપે.

DNS કેમ distributed છે?

એક જ centralized server પર overload, single point of failure, દૂરના clients માટે વધારે delay અને records update કરવાની મુશ્કેલી થાય. Hierarchical distributed design આ સમસ્યાઓ ઘટાડે છે.

યાદ રાખો: DNS = Name → IP. DHCP = Deviceને IP/config આપે. બંને ગૂંચવશો નહીં.

Port: DNS સામાન્ય રીતે UDP 53 વાપરે; કેટલાક responses/operations માટે TCP 53 પણ વપરાય છે.

Socket applicationને networkમાં data મોકલવા/મેળવવા interface આપે છે. PDFમાં બે socket types દર્શાવ્યાં છે:
