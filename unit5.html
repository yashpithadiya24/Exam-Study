2. Unit Testing, xUnit, Fact અને Theory

Unit test એક નાનાં code unitનું expected behavior ચકાસે છે. Testમાં Arrange, Act, Assert pattern વાપરો.

Arrange
test data તૈયાર
→
Act
method call
→
Assert
result verify
public class Calculator
{
    public int Add(int a, int b) => a + b;
}

using Xunit;
public class CalculatorTests
{
    [Fact]
    public void Add_TwoNumbers_ReturnsSum()
    {
        // Arrange
        var calc = new Calculator();
        // Act
        var result = calc.Add(2, 3);
        // Assert
        Assert.Equal(5, result);
    }

    [Theory]
    [InlineData(2, true)]
    [InlineData(3, false)]
    [InlineData(0, true)]
    public void IsEven_ReturnsExpected(int n, bool expected)
    {
        Assert.Equal(expected, n % 2 == 0);
    }
}
  • [Fact]: એક fixed test case.
  • [Theory]: same test logicને અનેક data rows સાથે ચલાવે.
  • [InlineData]: Theory માટે values આપે.
  • xUnit અને NUnit લોકપ્રિય .NET test frameworks છે.

3. Mocking અને Moq

Mock એટલે dependencyનું test માટેનું fake substitute, જે real database/network call કર્યા વગર behavior નિયંત્રિત અને verify કરવા દે.

public interface IProductRepository
{
    Task<Product?> GetByIdAsync(int id);
}
public class Product
{
    public int Id { get; set; }
    public string Name { get; set; } = "";
}
public class ProductService
{
    private readonly IProductRepository _repo;
    public ProductService(IProductRepository repo) => _repo = repo;
    public Task<Product?> GetAsync(int id) => _repo.GetByIdAsync(id);
}

// xUnit + Moq test
[Fact]
public async Task GetAsync_ReturnsProduct()
{
    var mock = new Mock<IProductRepository>();
    mock.Setup(r => r.GetByIdAsync(7))
        .ReturnsAsync(new Product { Id = 7, Name = "Pen" });

    var service = new ProductService(mock.Object);
    var result = await service.GetAsync(7);

    Assert.NotNull(result);
    Assert.Equal("Pen", result!.Name);
    mock.Verify(r => r.GetByIdAsync(7), Times.Once);
}

Setup() expected mock behavior ગોઠવે; ReturnsAsync() async result આપે; mock.Object fake dependency છે; Verify() call થયું કે નહીં ચકાસે; Times.Once એક call અપેક્ષિત કરે.

MoqNSubstitute
mock.Setup(x => x.Get()).Returns(value)sub.Get().Returns(value)
Explicit Setup/Verify style.Substitute object પર સીધું readable syntax.

4. SRP અને Separation of Concerns

Single Responsibility Principle (SRP): class પાસે બદલાવનું એક જ મુખ્ય કારણ હોવું જોઈએ. Controller request/HTTP સંભાળે; Service business logic; Repository data access.

Controller
HTTP, status codes
→
Service Layer
business rules
→
Repository
data access
→
Database

બધું controllerમાં લખવાથી class મોટો, coupled અને test કરવો મુશ્કેલ બને. Layer separationથી દરેક ભાગ અલગ test/change થઈ શકે.

5. Repository Pattern અને CRUD contract

Repository Pattern data accessને interface/classમાં isolate કરે છે. Service databaseની વિગત જાણ્યા વગર repository interface સાથે કામ કરે છે.

public interface IProductRepository
{
    Task<IReadOnlyList<Product>> GetAllAsync();
    Task<Product?> GetByIdAsync(int id);
    Task AddAsync(Product product);
    Task UpdateAsync(Product product);
    Task DeleteAsync(int id);
}
  • ફાયદા: testability, separation, data source બદલવાની સરળતા, repeated data-access code ઓછો.
  • સાવચેતી: EF Coreનું DbContext પહેલેથી repository/unit-of-work જેવી ક્ષમતાઓ આપે છે; ખૂબ generic wrapper હંમેશા જરૂરી નથી.

Service layer example

public class ProductService
{
    private readonly IProductRepository _repo;
    public ProductService(IProductRepository repo) => _repo = repo;

    public async Task<Product?> GetProductAsync(int id)
    {
        if (id <= 0) return null;
        return await _repo.GetByIdAsync(id);
    }
}

6. Dependency Injection (DI)

DI objectને તેની dependency બહારથી આપે છે. તે concrete implementationને સીધું new કરવાના બદલે interface દ્વારા coupling ઘટાડે છે.

// Program.cs
builder.Services.AddScoped<IProductRepository, ProductRepository>();
builder.Services.AddScoped<ProductService>();

// Controller
public ProductsController(ProductService service)
{
    _service = service;
}

Testingમાં production repositoryની જગ્યાએ Moq mock inject કરી શકાય. Lifetimes: Transient = દરેક resolution પર; Scoped = request scope; Singleton = app lifetime. DbContext સામાન્ય રીતે scoped હોય છે.

Exam answer flow: SRP (one responsibility) → layers (Controller-Service-Repository) → DI (interfaces injected) → mocks (dependency isolate) → tests (behavior verify).

7. Question Bank: લખવા લાયક ટૂંકા જવાબો

Q: Testing important કેમ?

Correctness, regression prevention, reliability, maintainability અને deployment પહેલાં defects શોધવા.

Q: Repository Pattern શું?

Data-access logicને abstraction પાછળ રાખતી design pattern; service/controller database implementationથી અલગ રહે.

Q: Mocking શા માટે?

Database/API જેવી external dependencyને isolate કરીને unit test ઝડપી, predictable અને repeatable બનાવવી.

Q: AAA શું?

Arrange = setup, Act = execute, Assert = expected result verify.
